## 7. 已接受的设计契约：V118/V121 幂等登记 ownership

2026-09-30 人工在收尾访谈中就第 6 节留下的 go/no-go 未决项选定「接受约束」分支，明确不引入 lease/expiry/recovery/reconciliation。本节记录该取舍的内容、代价和边界；它是工程取舍结论，不替代 R-011/R-029 的关闭证据，也不构成独立复核签字。

### 7.1 契约内容

- 对同一 `(tenant_id, process_definition_key, business_key)` 只保证**单一 winner**，不保证"每个调用者都能自行判定是否赢到"。
- ownership **只**由当前读 `SELECT ... FOR UPDATE`（`BpmProcessInstanceIdempotencyMapper.selectByUniqueKeyForUpdate`）返回的 `claim_token` 决定。
- 禁止用以下任一输入判定归属：`INSERT ... ON DUPLICATE KEY UPDATE` 是否抛出 `DuplicateKeyException`、其 affected rows、`LAST_INSERT_ID`。在 Connector/J 默认 `useAffectedRows=false` 下重复命中同样返回 affected rows 1；在 REPEATABLE-READ 下重复命中不抛 `DuplicateKeyException`，且普通一致性读可能看不到已提交的 winner 行——两个历史判定输入都不成立。
- `insertOrLockUniqueKey` 声明为 `void`，从结构上禁止把归属重新绑回 affected rows。

### 7.2 已接受的代价

- 空白登记（含 legacy `claim_token IS NULL`）会走无锁快路径持续 fail-closed 为 `PROCESS_INSTANCE_IDEMPOTENCY_PENDING`，**不回填、不重试抢占、无自动恢复**；需要人工介入才能解阻。
- V121 不回填 legacy NULL。
- 输家调用方必须按"稍后查询"处理，不得假定自己已创建成功。
- 生产大表 `ADD COLUMN` 的 MDL/表重建/复制风险仍未评估（属 G2 退出条件，未因接受本契约而免除）。

### 7.3 证据与代码锁

- 成因证据：`docs/enterprise-platform/evidence/production/v118-rr-consistency-read-mysql-20260930_000517.json`，SHA-256 `ad4f07005878d802adeb725f8e72fb7e82f3ad5eb2d994e199b71e84f5931bdb`（`.log` SHA-256 `d35631a440808b54c9cf5a62eb58e0b63a3bf735cda7293b804c98aeffd196f2`）。该证据为**隔离 MySQL 8.4.11 上的 SQL 级双会话探针**，不是应用链路、不是生产等价验证；未覆盖 `READ-COMMITTED / SERIALIZABLE` 对照。
- 代码锁：`zhicloud-module-bpm/src/test/java/cn/zhicloud/module/bpm/service/task/BpmProcessInstanceOwnershipContractTest.java` 断言三件事——抢占方法返回类型为 `void`；当前读返回他人 token 时判为输家且不回填 `process_instance_id`；空白登记 fail-closed 而不猜测归属。
