## 2. 对抗性审查：先证伪六个判断

1. **“IM / MP 未进构建” —— 假。**
   `zhicloud-server/pom.xml` 直接依赖 `zhicloud-module-im` 与 `zhicloud-module-mp`，并有 V155/V156 建表迁移；IM 有 30 个 Controller、MP 有 12 个。原根 README 第 88 行已纠正。

2. **“报表模块未接入 server” —— 假。**
   `zhicloud-module-report` 是 server 依赖，含 `GoViewDataController` / `GoViewProjectController`（`/report/go-view/data|project`），V154 建了 16 张 `jimu_*` 表。缺的是 GoView/积木报表**设计器独立部署**，不是模块未接入。原第 89 行已纠正。

3. **“业务模块互相耦合严重” —— 假。**
   最大业务→业务 import 是 crm→system 56，且 system 是底座。真正的高耦合只存在于各模块对 `framework/common` 的依赖，这是单体的正常形态。

4. **“仓库里有一大批死代码” —— 未证实。**
   文本扫描得到 57 个“无引用类”，抽查后几乎全是 Spring 自动配置、按接口注入的 `@Service`、`spring.factories` / `AutoConfiguration.imports` 注册项。**Spring Bean 的存活性不能靠 grep 判定**，误删会在启动期才炸。

5. **“FMS 是没上线的死模块” —— 假。**
   FMS 有 V157 建表、V158 菜单、V159 字典、V190 ERP 财务合并、V191/V193 科目账簿联动；库内 14 条菜单、前端 64 个文件。按“SQL 里没有 fms 字样”去删会误杀（我第一次检索只扫了 `sql/`，漏了 `zhicloud-server/src/main/resources/db/migration`）。

6. **“`sql/dm/flowable-patch` 是死代码” —— 不准确。**
   它确实不在 Maven reactor 内，但 01/06/12/13/14 多份文档承诺达梦 DM8 支持，补丁是 DM 适配资产。属于“未构建的资产”，不是垃圾。

## 3. 第一性原理：哪些是核心，哪些是可选面

这个产品的不可约核心只有四件事：**租户隔离 + RBAC、业务域数据、审批流、审计**。其余都是可选面：

- 8 套 SQL 方言（只有 MySQL 被真实执行过）；
- AI / RAG / 多智能体（默认关闭，依赖外部 Key）；
- 数据湖（Iceberg + Trino，默认关闭）；
- IM / MP / 报表设计器 / 大屏；
- 9 个前端主题与大量 CRUD 页面。

奥卡姆剃刀应该砍**可选面的默认开启与交付承诺**，而不是砍核心域的代码。因此“精简”分两条腿：

1. **默认关闭**：可选面不进默认启动路径，代码保留、能力不丢；
2. **内部去重**：超长类拆分、重复模板收敛。

## 4. 消融实验矩阵

判定规则：关闭某机制后，跑 **104 个 server 用例 + 403 菜单 smoke + 对应业务链路**；全绿 = 该机制对本次试点非必需（可默认关闭，不删除）；任一红 = 必要，保留并补测试。

| 机制 | 现有开关 | 关闭后必须跑 | 备注 |
|---|---|---|---|
| 多租户 | `zhicloud.tenant.enable=false` | 登录 + 跨租户隔离用例 | 关掉会破坏隔离，预期“红”，用于证明必要性 |
| Outbox / Inbox | `zhicloud.integration.enabled=false`、`relay-enabled=false` | 跨模块事件链路 | 需先确认哪些业务依赖异步事件 |
| 库存双写 | `zhicloud.inventory.enabled=false` | ERP/MES/WMS 库存一致性 | 关的是整个 inventory starter，不只是双写 |
| 主数据 MDM | `zhicloud.mdm.enabled=false` | 物料/供应商映射链路 | |
| AI / RAG | `zhicloud.airag.enabled=false`（默认关） | AI 页面降级 | 已经是默认关，主要验证“关掉不影响主流程” |
| 数据权限 | 无全局开关 | 7 角色矩阵 + CRM 列表 | 只能代码级消融，风险高，先补测试 |

## 6. 为什么本轮不直接删业务代码

- 461 个测试类不等于 461 个可依赖的回归用例；`zhicloud-server` 最近一次只有 104 个。
- Spring 的死代码判定无法静态证明（§2.4、§2.5 两个反例）。
- 任何删除都要回答“哪个用例证明它没用”；目前回答不了。
- 因此只做**编译器可证明**或**消融可证明**的改动；其余先补测试。
