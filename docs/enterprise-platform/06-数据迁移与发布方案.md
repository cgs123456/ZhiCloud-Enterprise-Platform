# 06 数据迁移与发布方案

## 1. 核心原则

1. 已应用的 Flyway 迁移不可直接修改，避免 checksum 漂移。
2. 所有修复使用新增、幂等、可回滚或可补偿的迁移。
3. 生产 Secret 不进入 SQL、Git、镜像或日志。
4. 先扩展、后迁移、再收缩（Expand -> Migrate -> Contract）。
5. 迁移必须支持租户隔离、数据量分批和失败重试。
6. 每个迁移必须有验证脚本和回滚/补偿说明。
7. 先影子运行，再预发，再生产；每步留证据。

### 2.1 管理员 bootstrap 与执行顺序

生产管理员由 `zhicloud-server/src/main/java/cn/zhicloud/server/BootstrapAdminRunner.java` 在 K8s Job 中初始化，不是由 Python 模板渲染器或模板 SQL 直接初始化。默认非种子用户名为 `zhicloud_admin`，固定 `tenant_id=1`，绑定 `role_id=1`、`post_id=4`，不固定用户 `id=1`，密码使用 BCrypt cost 12。

`BOOTSTRAP_ADMIN_MODE=ensure` 是默认模式：账号不存在时创建用户及角色/岗位绑定；账号已存在且密码匹配时执行 noop，并修复缺失的角色/岗位绑定；账号已存在但密码不一致时 fail-closed、返回非零且不得覆盖原密码哈希。`rotate` 仅用于受控的 break-glass 密码轮换，不提供覆盖既有密码的强制写入模式。密码至少 12 个字符、UTF-8 编码最长 72 字节，并拒绝公开种子用户名。管理员密码只能来自专用 Secret，不得进入 Git、ConfigMap、values、镜像、日志或证据文件。

Helm 模板 `deploy/helm/zhicloud/templates/job-bootstrap-admin.yaml` 的 `bootstrapAdmin.enabled` 默认是 `false`，即默认 fail-closed；显式启用时必须提供 `bootstrapAdmin.passwordSecretName`、`bootstrapAdmin.passwordSecretKey`，MySQL TLS 启用时还必须提供 truststore Secret。clean 模式启用 bootstrap 但关闭 migration 时，Helm 渲染应直接失败。

顺序必须区分存量库和 clean 新库：

1. **存量库**：bootstrap Job 使用 sync-wave `-2`，先于使用 sync-wave `-1` 的迁移 Job。先以 `ensure` 创建或校验非种子管理员及角色/岗位绑定，再运行迁移；迁移按 V115 清理公开种子账号、V116 建立活跃账号唯一约束、V117 建立 CRM 回款幂等约束、V118 建立 BPM 流程实例幂等登记、V119 建立库存租户唯一约束、V120 建立 Outbox/Inbox owner/lease、V121 建立 BPM claim_token ownership 的顺序执行并验证。本次尚未完成该顺序的存量生产库闭环。
2. **clean 新库**：迁移 Job 使用 sync-wave `-1`，先以 `MIGRATION_BASELINE_MODE=clean` 执行 clean baseline 和 V2..V121；bootstrap Job 使用 sync-wave `0`，迁移完成后初始化管理员；之后才开放滚动业务副本。
3. 无论哪条路径，都不能先开放业务流量再补管理员权限，也不能在未验证 bootstrap 返回码和只读审计前继续发布。

历史 runner 证据为 `docs/enterprise-platform/evidence/production/mysql-runner-sandbox-20260927_191941.json` 和 `mysql-runner-sandbox-20260927_191941-audit.json`。该 MySQL 8.4.9 沙箱验证了 ensure 创建、相同密码 noop、不同密码 fail-closed 且哈希不变、rotate 成功、旧密码失效、新密码 noop，并复核了账号、租户、角色、岗位、BCrypt 形态和唯一索引；当前 T-000 另以 `docs/enterprise-platform/evidence/production/mysql-history-lock-20260929_094909.json` 在隔离 MySQL 8.4.11 验证 history 锁；上述证据均不覆盖生产目标库，`independent_review=false`。

边界和风险：

- MySQL 8.4.x clean 沙箱已完成 V115-V118 的实库执行（服务端精确版本以各证据为准）；V119/V120/V121 另有隔离 MySQL 8.4.11 沙箱/静态证据（V119 4/4；V120 首次/幂等重跑 exit=0、4/4 验证和不兼容索引 fail-closed；V121 claim-token unit 4/0/0/0、真实链 fail-closed 2/0/0/0、10 并发 1/0/0/0、SQL lint 2 文件 0 违规）；PostgreSQL、Highgo、Kingbase、OpenGauss、Oracle、SQL Server、DM8 尚未在目标实库执行。静态渲染或契约测试不能证明方言语法、事务边界、并发、`RETURNING` 或序列行为，必须逐库验收。
- MySQL 的 V116 已在 clean 沙箱真实执行并重跑幂等，`(tenant_id, active_username)` 唯一索引实际名称为 `uk_system_users_tenant_active_username`；并发插入和软删除后重建已在隔离 MySQL 沙箱验证；生产规模 MDL/表重建/磁盘/复制影响尚未验证。非 MySQL 仍只有 `username` 普通索引，脚本层 `COUNT(*)` 守卫能阻断存量重复，但不能替代并发下的数据库约束。
- 8 套全新安装脚本现在都定义了 `totp_secret` / `totp_enabled`，但非 MySQL 存量库没有对应升级迁移，SQL Server 新列也没有扩展属性注释；`int2`/`bit` 与 `Boolean totpEnabled` 的映射和登录链路必须在目标实库确认。
- V117 是 MySQL 专用 CRM 回款幂等迁移，已在 clean 沙箱真实执行并重跑幂等，唯一索引实际名称为 `uk_crm_receivable_idempotency`；并发重复请求和软删除永久占用已在隔离 MySQL 沙箱验证；生产规模 MDL/表重建/磁盘/复制影响尚未验证，非 MySQL 没有等价迁移。存量重复幂等键、键/指纹不成对或非法指纹会 fail-closed，不自动清理业务数据。
- 本地 Helm 3.22.0/4.3.0 渲染、lint、6 个正向、10 个负向 fail-closed 和离线 K8s schema 校验已通过（`helm-render-20260929_202001.json`）；K8s 服务端 dry-run、真实 Secret 注入、MySQL TLS 握手和证书链仍未验证。

## 3. 建议的迁移序列

### V115：生产种子账号和客户端凭据清理（已实现，clean 沙箱已执行，存量库待闭环）

目标：

- 识别并禁用/删除生产迁移引入的历史种子账号。
- 禁用历史 OAuth2/社交客户端配置。
- 不写入任何真实 Secret。
- 记录清理审计。

当前实现策略：

```text
1. 对已知种子账号按用户名匹配；
2. 如果账号从未登录或属于演示账号，则 status=1 且 deleted=1；
3. 如果账号已有真实业务关联，先禁用、通知负责人、人工迁移权限，再删除；
4. OAuth2/社交客户端先 status=1，不直接删除，保留审计；
5. 真实客户端 Secret 由部署时从 Vault/KMS 注入并轮换；
6. 迁移幂等，可重复执行。
```

注意：

- 不能简单把所有历史账号删除，必须先做影响分析。
- 不能把真实 Secret 写进迁移。
- 不能用占位符替换后仍然保持启用。

### V116：MySQL 活跃账号租户级唯一约束（已实现，clean 沙箱已执行并重跑幂等）

- 增加 `active_username` STORED 生成列：`deleted = 0` 时取 `username`，软删除时为 `NULL`。
- 增加 `uk_system_users_tenant_active_username(tenant_id, active_username)` 唯一索引，阻止并发创建同租户活跃重复账号。
- 发现存量活跃重复时 fail-closed，不自动删除或改名业务数据。
- 迁移会校验已有生成列和索引定义，避免人工改动后误判幂等。
- 边界：这是 MySQL 专用迁移，已在 clean 沙箱执行；并发插入、软删除后重建、大表 `ADD COLUMN`/`ADD UNIQUE KEY` 的 MDL、表重建、磁盘和复制延迟未验证；非 MySQL 没有等价迁移。

### V117：CRM 回款租户级幂等约束（已实现，clean 沙箱已执行并重跑幂等）

- 为 `crm_receivable` 增加 `idempotency_key` 和 `payload_hash` 可空列，兼容历史数据。
- 增加 `uk_crm_receivable_idempotency(tenant_id, idempotency_key)` 唯一索引，阻止并发重复创建回款。
- 幂等键采用永久占用语义：软删除不释放；键和指纹必须同时存在或同时为空，指纹必须是 64 位十六进制 SHA-256。
- 存量重复、非法配对或非法定义 fail-closed，不自动清理业务数据。
- 边界：这是 MySQL 专用迁移，已在 clean 沙箱执行；并发重复请求、软删除永久占用、大表 `ADD COLUMN`/`ADD UNIQUE KEY` 的 MDL、表重建、磁盘和复制延迟未验证；非 MySQL 没有等价迁移。
- V117 与 V118 的联合真实链证据见下一节；V117 自身仍需完成生产规模 MDL/表重建/磁盘/复制和非 MySQL 等价方案验证。

### V118：BPM 流程实例幂等登记（已实现，clean 沙箱已执行；隔离 MySQL 真实链已覆盖）
- 新增 `bpm_process_instance_idempotency`，以 `(tenant_id, process_definition_key, business_key)` 唯一键阻止同一租户、同一流程定义下的重复实例创建。
- `process_instance_id` 在 Flowable 启动成功后回填；重入请求返回既有实例，软删除仍永久占用唯一键。
- 创建流程失败时，登记行与 Flowable 历史必须在同一事务中回滚；该语义已在隔离 MySQL 8.4.11 的真实 BPM 服务链中验证。
- 当前隔离 MySQL 8.4.11 已验证 CRM 本地事务、V118 幂等登记和 Flowable 历史的提交一致与共同回滚（2/2）、同 `businessKey` 10 并发请求返回同一实例（1/1）和动态数据源路由/事务绑定 3/3；流程定义查询等非目标依赖仍为 mock。生产 `DynamicRoutingDataSource`/物理主从/真实读写分离/多租户物理连接、网络/数据库/进程故障、生产规模和 Outbox/补偿/对账仍未验证；一旦拆分服务或切换数据源，BPM 实例与本地状态仍可能不一致。`businessKey` 本身不提供唯一性保证。
- 边界：这是 MySQL 专用迁移；流程定义查询等非目标依赖仍为 mock。生产 `DynamicRoutingDataSource`/物理主从/真实读写分离/多租户物理连接、网络/数据库/进程故障、生产规模、Outbox/补偿和对账未验证。

### V121：BPM 流程实例幂等 claim_token ownership（已实现；隔离/静态验证，非生产）
- 新增 `claim_token varchar(64) NULL DEFAULT NULL`；插入抢占时写入本次调用的 UUID token，重复命中不覆盖既有 token，应用通过 `selectByUniqueKeyForUpdate` 校验 ownership。
- `process_instance_id` 非空时返回既有实例；token 不匹配（包括空白登记和 legacy NULL）时 fail-closed 为 `PROCESS_INSTANCE_IDEMPOTENCY_PENDING`，不再继续创建流程实例。
- V121 验证脚本对表/列缺失或定义不兼容 fail-closed，迁移本身幂等；不回填 legacy NULL、不改写业务行。
- 边界：MySQL 专用；无 lease/expiry/recovery/reconciliation，空白登记会永久阻塞同一唯一键；软删除仍占唯一键，逻辑删除过滤可能使唯一键命中后的 select 返回 null；存量大表 `ADD COLUMN` 可能触发表重建或长时间 MDL，生产前需评估备份、磁盘、复制延迟和低峰窗口。
- 已接受的设计契约（2026-09-30 人工选定，详见 `05-生产就绪门禁清单.md` 第 7 节）：对同一 `(tenant_id, process_definition_key, business_key)` 只保证单一 winner，ownership 只由 `selectByUniqueKeyForUpdate` 当前读返回的 `claim_token` 决定；禁止以 `ON DUPLICATE KEY UPDATE` 是否抛异常或其 affected rows 判定归属——隔离 MySQL 8.4.11 探针实证在 REPEATABLE-READ 下重复命中既不抛 `DuplicateKeyException`，且 Connector/J 默认 `useAffectedRows=false` 时同样返回 1，两个输入都不可靠。`insertOrLockUniqueKey` 声明为 `void` 以从结构上排除该退化路径，由 `BpmProcessInstanceOwnershipContractTest` 锁定。此取舍不关闭 R-011/R-029，也不是生产等价验证。
- 证据：`zhicloud-server/src/main/resources/db/migration/V121__bpm_process_instance_idempotency_claim_token.sql`（SHA-256 `9597f047324b1a7f7348a050eebf302f6fabf505c642cf4ede5f60a54f8093e0`）、`zhicloud-server/src/main/resources/db/verification/V121_verify.sql`（SHA-256 `23760521d1fbb2dc0c4388fcd798e4278019287a34a82cdc4372817070cd61d2`）、汇总证据 `docs/enterprise-platform/evidence/production/bpm-idempotency-real-chain-claim-token-20260929_215500.json`（SHA-256 `8fc10375e4118c3f2310abc7acb9c6b1f3f92e83996628aac22918e0899437fa`）。

## 4. 数据迁移阶段

### 阶段 0：冻结与盘点

- 冻结生产 schema 变更。
- 导出表结构、索引、约束、数据量、租户分布。
- 标记敏感字段、主数据、业务单据、财务数据、质量数据。
- 建立数据字典和责任人。

### 阶段 1：备份与恢复验证

- 全量备份 + binlog/PITR。
- 在隔离环境恢复。
- 验证恢复后的数据一致性。
- 记录 RTO/RPO 实测值。

### 阶段 2：影子运行

- 在沙箱执行全部迁移。
- 运行验证脚本。
- 重跑迁移验证幂等。
- 运行 V116/V117 约束语义沙箱，核对并发 1062、软删除语义和 100,000 行合成 DDL 观测；并复跑 V118 BPM 真实链和并发幂等测试；不得把这些隔离证据替代生产规模、生产数据源或生产故障演练。
- 对 bootstrap 管理员执行只读审计，核对账号、租户、角色、岗位、哈希形态和唯一索引；核对当前证据哈希并记录 `independent_review` 状态。
- 做失败注入和回滚演练。

### 阶段 3：预发迁移

- 使用接近生产的数据量和配置。
- 跑业务回归和集成测试。
- 验证迁移时间、锁表、索引、连接池和告警。

### 阶段 4：生产迁移

- 发布窗口、审批、回滚条件。
- 迁移 Job 先执行，应用后启动。
- 实时观察数据库、应用、Outbox、DLQ。
- 失败立即停止并回滚/补偿。

### 阶段 5：对账与收尾

- 库存、财务、质量、回款、运单日终对账。
- 差异工单处理。
- 迁移报告归档。

## 5. 发布策略

### 应用发布

- 优先滚动发布；关键变更使用金丝雀。
- 健康检查通过后才接流量。
- 迁移不兼容时禁止旧版本继续写入。
- 明确回滚版本和数据库回滚/补偿策略。

### 数据发布

- 大表迁移分批执行，避免长事务和锁表。
- 新增列先允许空，再回填，再加约束。
- 索引使用在线或低峰创建。
- 删除旧字段前至少保留一个发布周期。

## 6. 回滚与补偿

| 变更 | 回滚方式 |
|---|---|
| 新增表/列 | 保留，不立即删除 |
| 数据清理 | 先逻辑删除，保留审计和恢复脚本 |
| 活跃账号唯一约束 | 回滚前确认应用已恢复兼容校验；保留重复账号风险登记和补偿方案 |
| BPM claim_token ownership | 回滚前必须回退到不依赖 `claim_token` ownership 的应用版本；完成空白登记对账并确认 legacy NULL/软删除行为；保留 V121 列和回滚/补偿记录，不自动回填或清理业务行 |
| CRM 回款幂等约束 | 回滚前确认应用已恢复兼容校验；隔离 MySQL 8.4.11 已证明 CRM/BPM/Flowable 共同提交与回滚（2/2）、同 `businessKey` 10 并发幂等（1/1）和动态数据源路由/事务绑定 3/3；保留生产物理主从/真实读写分离/多租户数据源拓扑、生产故障、生产规模及 Outbox/补偿/对账风险登记 |
| Secret 轮换 | 双密钥过渡、验证后撤销旧密钥 |
| 库存真值 | 保留双写和差异表，允许切回只读对账 |
| 事件消费 | DLQ 重放和补偿命令 |
| 应用版本 | 镜像回滚 + 兼容 schema |

## 7. 数据质量门禁

迁移前后至少检查：

- 行数、主键、外键、唯一约束。
- 租户字段和索引。
- 金额、数量精度。
- 库存恒等式。
- 财务借贷平衡。
- 质检状态和业务状态一致。
- 事件幂等键唯一。
- 同一租户活跃账号名唯一；软删除重建路径有验证。
- CRM 回款幂等键同租户唯一；键/指纹成对且指纹合法；软删除永久占用语义有验证。
- BPM 幂等登记 `claim_token` 形态合法；空白登记（含 legacy NULL）已对账并明确人工回收或补偿路径。
- BPM 幂等登记与 Flowable 运行时/历史对账完成；不得把空白登记永久阻塞视为通过。
- 敏感字段加密/脱敏。

## 8. 结论

迁移方案的核心不是“把 SQL 跑完”，而是：

> **保证历史数据不丢、业务不中断、租户不串、财务不重复、库存可对账、失败可回滚。**
