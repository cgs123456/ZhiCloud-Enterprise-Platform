# 06 数据迁移与发布方案

## 1. 核心原则

1. 已应用的 Flyway 迁移不可直接修改，避免 checksum 漂移。
2. 所有修复使用新增、幂等、可回滚或可补偿的迁移。
3. 生产 Secret 不进入 SQL、Git、镜像或日志。
4. 先扩展、后迁移、再收缩（Expand -> Migrate -> Contract）。
5. 迁移必须支持租户隔离、数据量分批和失败重试。
6. 每个迁移必须有验证脚本和回滚/补偿说明。
7. 先影子运行，再预发，再生产；每步留证据。

## 2. 当前迁移基线

- 当前工作区最近迁移：V117（已在 MySQL 8.4.9 clean 沙箱执行并重跑幂等；V116/V117 并发、软删除语义和 100,000 行合成 DDL 成本已有隔离沙箱证据；存量库全链尚未通过）。
- `scripts/production/migration-contract.json` 覆盖 V90-V117。
- 已有 V100-V107 集成、租户、DLQ 基础。
- 已有 V108 租户隔离、V109 WMS 唯一约束、V110-V114 业务和 AI 表、V115 生产种子账号/演示客户端禁用、V116 MySQL 活跃账号唯一约束，以及 V117 MySQL CRM 回款幂等约束；V115-V117 已在 clean 沙箱真实执行；V116/V117 并发、软删除语义和 100,000 行合成 DDL 成本另有隔离沙箱证据。
- V1.1 基础迁移仍包含历史种子账号和客户端凭据，**不能直接编辑 V1.1**。

### 2.1 管理员 bootstrap 与执行顺序

生产管理员由 `zhicloud-server/src/main/java/cn/zhicloud/server/BootstrapAdminRunner.java` 在 K8s Job 中初始化，不是由 Python 模板渲染器或模板 SQL 直接初始化。默认非种子用户名为 `zhicloud_admin`，固定 `tenant_id=1`，绑定 `role_id=1`、`post_id=4`，不固定用户 `id=1`，密码使用 BCrypt cost 12。

`BOOTSTRAP_ADMIN_MODE=ensure` 是默认模式：账号不存在时创建用户及角色/岗位绑定；账号已存在且密码匹配时执行 noop，并修复缺失的角色/岗位绑定；账号已存在但密码不一致时 fail-closed、返回非零且不得覆盖原密码哈希。`rotate` 仅用于受控的 break-glass 密码轮换，不提供覆盖既有密码的强制写入模式。密码至少 12 个字符、UTF-8 编码最长 72 字节，并拒绝公开种子用户名。管理员密码只能来自专用 Secret，不得进入 Git、ConfigMap、values、镜像、日志或证据文件。

Helm 模板 `deploy/helm/zhicloud/templates/job-bootstrap-admin.yaml` 的 `bootstrapAdmin.enabled` 默认是 `false`，即默认 fail-closed；显式启用时必须提供 `bootstrapAdmin.passwordSecretName`、`bootstrapAdmin.passwordSecretKey`，MySQL TLS 启用时还必须提供 truststore Secret。clean 模式启用 bootstrap 但关闭 migration 时，Helm 渲染应直接失败。

顺序必须区分存量库和 clean 新库：

1. **存量库**：bootstrap Job 使用 sync-wave `-2`，先于使用 sync-wave `-1` 的迁移 Job。先以 `ensure` 创建或校验非种子管理员及角色/岗位绑定，再运行迁移；迁移按 V115 清理公开种子账号、V116 建立活跃账号唯一约束、V117 建立 CRM 回款幂等约束的顺序执行并验证。本次尚未完成该顺序的存量生产库闭环。
2. **clean 新库**：迁移 Job 使用 sync-wave `-1`，先以 `MIGRATION_BASELINE_MODE=clean` 执行 clean baseline 和 V2..V117；bootstrap Job 使用 sync-wave `0`，迁移完成后初始化管理员；之后才开放滚动业务副本。
3. 无论哪条路径，都不能先开放业务流量再补管理员权限，也不能在未验证 bootstrap 返回码和只读审计前继续发布。

当前有效证据为 `docs/enterprise-platform/evidence/production/mysql-runner-sandbox-20260927_191941.json` 和 `mysql-runner-sandbox-20260927_191941-audit.json`。该沙箱验证了 ensure 创建、相同密码 noop、不同密码 fail-closed 且哈希不变、rotate 成功、旧密码失效、新密码 noop，并复核了账号、租户、角色、岗位、BCrypt 形态和唯一索引；`independent_review=false`。

边界和风险：

- 仅 MySQL 8.4.9 clean 沙箱完成实库执行；PostgreSQL、Highgo、Kingbase、OpenGauss、Oracle、SQL Server、DM8 尚未在目标实库执行。静态渲染或契约测试不能证明方言语法、事务边界、并发、`RETURNING` 或序列行为，必须逐库验收。
- MySQL 的 V116 已在 clean 沙箱真实执行并重跑幂等，`(tenant_id, active_username)` 唯一索引实际名称为 `uk_system_users_tenant_active_username`；并发插入和软删除后重建已在隔离 MySQL 沙箱验证；生产规模 MDL/表重建/磁盘/复制影响尚未验证。非 MySQL 仍只有 `username` 普通索引，脚本层 `COUNT(*)` 守卫能阻断存量重复，但不能替代并发下的数据库约束。
- 8 套全新安装脚本现在都定义了 `totp_secret` / `totp_enabled`，但非 MySQL 存量库没有对应升级迁移，SQL Server 新列也没有扩展属性注释；`int2`/`bit` 与 `Boolean totpEnabled` 的映射和登录链路必须在目标实库确认。
- V117 是 MySQL 专用 CRM 回款幂等迁移，已在 clean 沙箱真实执行并重跑幂等，唯一索引实际名称为 `uk_crm_receivable_idempotency`；并发重复请求和软删除永久占用已在隔离 MySQL 沙箱验证；生产规模 MDL/表重建/磁盘/复制影响尚未验证，非 MySQL 没有等价迁移。存量重复幂等键、键/指纹不成对或非法指纹会 fail-closed，不自动清理业务数据。
- 本地 Helm 3.22.0/4.3.0 渲染、lint、fail-closed 和离线 K8s schema 校验已通过（`helm-render-20260927_212935.json`）；K8s 服务端 dry-run、真实 Secret 注入、MySQL TLS 握手和证书链仍未验证。

## 3. 建议的迁移序列

### V115：生产种子账号和客户端凭据清理（已实现，clean 沙箱已执行，存量库待闭环）

目标：

- 识别并禁用/删除生产迁移引入的历史种子账号。
- 禁用历史 OAuth2/社交客户端配置。
- 不写入任何真实 Secret。
- 记录清理审计。

当前实现策略：

```text
1. 对已知种子账号按用户名匹配；
2. 如果账号从未登录或属于演示账号，则 status=1 且 deleted=1；
3. 如果账号已有真实业务关联，先禁用、通知负责人、人工迁移权限，再删除；
4. OAuth2/社交客户端先 status=1，不直接删除，保留审计；
5. 真实客户端 Secret 由部署时从 Vault/KMS 注入并轮换；
6. 迁移幂等，可重复执行。
```

注意：

- 不能简单把所有历史账号删除，必须先做影响分析。
- 不能把真实 Secret 写进迁移。
- 不能用占位符替换后仍然保持启用。

### V116：MySQL 活跃账号租户级唯一约束（已实现，clean 沙箱已执行并重跑幂等）

- 增加 `active_username` STORED 生成列：`deleted = 0` 时取 `username`，软删除时为 `NULL`。
- 增加 `uk_system_users_tenant_active_username(tenant_id, active_username)` 唯一索引，阻止并发创建同租户活跃重复账号。
- 发现存量活跃重复时 fail-closed，不自动删除或改名业务数据。
- 迁移会校验已有生成列和索引定义，避免人工改动后误判幂等。
- 边界：这是 MySQL 专用迁移，已在 clean 沙箱执行；并发插入、软删除后重建、大表 `ADD COLUMN`/`ADD UNIQUE KEY` 的 MDL、表重建、磁盘和复制延迟未验证；非 MySQL 没有等价迁移。

### V117：CRM 回款租户级幂等约束（已实现，clean 沙箱已执行并重跑幂等）

- 为 `crm_receivable` 增加 `idempotency_key` 和 `payload_hash` 可空列，兼容历史数据。
- 增加 `uk_crm_receivable_idempotency(tenant_id, idempotency_key)` 唯一索引，阻止并发重复创建回款。
- 幂等键采用永久占用语义：软删除不释放；键和指纹必须同时存在或同时为空，指纹必须是 64 位十六进制 SHA-256。
- 存量重复、非法配对或非法定义 fail-closed，不自动清理业务数据。
- 边界：这是 MySQL 专用迁移，已在 clean 沙箱执行；并发重复请求、软删除永久占用、大表 `ADD COLUMN`/`ADD UNIQUE KEY` 的 MDL、表重建、磁盘和复制延迟未验证；非 MySQL 没有等价迁移。
- 当前模块化单体、单主数据源部署下，CRM 本地事务与 Flowable 很可能共享 Spring 事务，但物理数据源路由和真实回滚尚未证明；一旦拆分服务或切换数据源，BPM 实例与本地状态可能不一致。`businessKey` 本身不提供唯一性保证，上线前仍需故障注入验证、业务键唯一/幂等和必要的 Outbox/补偿。

### 规划 P-INV-01：库存真值迁移（不是 Flyway 版本号）

- 确认 WMS 为库存权威源。
- 为 ERP/MES 增加投影表或同步字段。
- 建立库存流水与对账表。
- 迁移前统计三套库存差异。
- 过渡期双写 + 日终对账。
- 差异处理完成后停止非 WMS 写入口。

### 规划 P-QMS-01：质量门禁（不是 Flyway 版本号）

- 质检状态与收货/流转/发运绑定。
- 增加放行查询接口和必要索引。
- 不合格品进入 NCR/CAPA。
- 质检规则版本化。

### 规划 P-FIN-01：财务过账和对账（不是 Flyway 版本号）

- 业务单据到会计事件到凭证的关联。
- 幂等键、期间、冲销、对账表。
- 期末结账和异常处理。

### 规划 P-API-01：模块 API 和事件契约（不是 Flyway 版本号）

- 建立事件版本、租户、幂等键、追踪 ID。
- 跨模块依赖清单和门禁。
- 旧接口兼容和下线计划。

> V117 已被 CRM 回款幂等迁移占用；上述 `P-*` 是规划编号，不等于实际 Flyway 版本号，实施时必须在 `migration-contract.json` 下重新分配并登记。

## 4. 数据迁移阶段

### 阶段 0：冻结与盘点

- 冻结生产 schema 变更。
- 导出表结构、索引、约束、数据量、租户分布。
- 标记敏感字段、主数据、业务单据、财务数据、质量数据。
- 建立数据字典和责任人。

### 阶段 1：备份与恢复验证

- 全量备份 + binlog/PITR。
- 在隔离环境恢复。
- 验证恢复后的数据一致性。
- 记录 RTO/RPO 实测值。

### 阶段 2：影子运行

- 在沙箱执行全部迁移。
- 运行验证脚本。
- 重跑迁移验证幂等。
- 运行 V116/V117 约束语义沙箱，核对并发 1062、软删除语义和 100,000 行合成 DDL 观测；不得把该证据替代生产规模演练。
- 对 bootstrap 管理员执行只读审计，核对账号、租户、角色、岗位、哈希形态和唯一索引；核对当前证据哈希并记录 `independent_review` 状态。
- 做失败注入和回滚演练。

### 阶段 3：预发迁移

- 使用接近生产的数据量和配置。
- 跑业务回归和集成测试。
- 验证迁移时间、锁表、索引、连接池和告警。

### 阶段 4：生产迁移

- 发布窗口、审批、回滚条件。
- 迁移 Job 先执行，应用后启动。
- 实时观察数据库、应用、Outbox、DLQ。
- 失败立即停止并回滚/补偿。

### 阶段 5：对账与收尾

- 库存、财务、质量、回款、运单日终对账。
- 差异工单处理。
- 迁移报告归档。

## 5. 发布策略

### 应用发布

- 优先滚动发布；关键变更使用金丝雀。
- 健康检查通过后才接流量。
- 迁移不兼容时禁止旧版本继续写入。
- 明确回滚版本和数据库回滚/补偿策略。

### 数据发布

- 大表迁移分批执行，避免长事务和锁表。
- 新增列先允许空，再回填，再加约束。
- 索引使用在线或低峰创建。
- 删除旧字段前至少保留一个发布周期。

## 6. 回滚与补偿

| 变更 | 回滚方式 |
|---|---|
| 新增表/列 | 保留，不立即删除 |
| 数据清理 | 先逻辑删除，保留审计和恢复脚本 |
| 活跃账号唯一约束 | 回滚前确认应用已恢复兼容校验；保留重复账号风险登记和补偿方案 |
| CRM 回款幂等约束 | 回滚前确认应用已恢复兼容校验；保留重复回款、BPM 事务回滚未证明和幂等/补偿风险登记 |
| Secret 轮换 | 双密钥过渡、验证后撤销旧密钥 |
| 库存真值 | 保留双写和差异表，允许切回只读对账 |
| 事件消费 | DLQ 重放和补偿命令 |
| 应用版本 | 镜像回滚 + 兼容 schema |

## 7. 数据质量门禁

迁移前后至少检查：

- 行数、主键、外键、唯一约束。
- 租户字段和索引。
- 金额、数量精度。
- 库存恒等式。
- 财务借贷平衡。
- 质检状态和业务状态一致。
- 事件幂等键唯一。
- 同一租户活跃账号名唯一；软删除重建路径有验证。
- CRM 回款幂等键同租户唯一；键/指纹成对且指纹合法；软删除永久占用语义有验证。
- 敏感字段加密/脱敏。

## 8. 结论

迁移方案的核心不是“把 SQL 跑完”，而是：

> **保证历史数据不丢、业务不中断、租户不串、财务不重复、库存可对账、失败可回滚。**
