# 02 企业级能力差距分析

## 1. 评估方法

采用“能力等级 + 业务风险 + 证据强度”三重判断：

| 等级 | 定义 |
|---|---|
| L0 | 没有能力 |
| L1 | 有 CRUD 或演示能力 |
| L2 | 单域可运行，但缺少跨域闭环 |
| L3 | 多域闭环、有并发/幂等/对账/审计，有生产证据 |
| L4 | 多组织、多租户、合规、可扩展、可运营 |

**注意：模块数量和 Controller 数量只能说明覆盖面，不能直接提升等级。**

## 3. 根因分析

### 3.1 功能广度领先于业务一致性

平台拥有大量 Controller 和表，但跨模块链路缺少统一事务边界、补偿、幂等和对账。典型风险包括：

- ERP、WMS、MES 存在多套库存语义。
- 质检结论没有成为入库和生产放行的强制门禁。
- 工单、合同、回款等累计量缺少并发保护。
- 单据状态可以绕过中间环节直接完成。

### 3.2 模块化单体边界不够硬

模块同仓库、同数据库，容易被“能 import 就直接 import”破坏边界。目标不是立即拆微服务，而是：

1. 每个业务模块提供 `api` 包。
2. 跨模块只依赖 `api` 的接口和 DTO。
3. 禁止跨模块直接依赖 DAL、Mapper、DO。
4. 跨域一致性通过事件、Outbox/Inbox、补偿和对账实现。

### 3.3 生产工程证据不足

已有 Maven、Python、迁移契约、静态扫描和 Helm 模板，但仍缺少：

- 真实 TLS 握手与证书链
- 真实 K8s 服务端 dry-run
- 真实生产环境部署
- 备份恢复和灾备演练
- 压测、长稳、故障注入
- SLO、告警、on-call

### 3.4 安全门禁仍为红灯

当前安全扫描仍为失败。P0 由以下两类业务风险构成，必须修复数据或受控迁移，不能修改断言：

- 20 条生产 Flyway 种子账号。
- 12 条 `V1.1` 明文客户端凭据；8 套安装脚本中的 96 条已移除，但真实 Secret 轮换和旧值失效仍未验证。

此前 3 条 `existingSecret` 空值命中已确认是扫描器假阳性并修复，R5 当前为 0，不计入 P0。

## 5. 建议的优先级原则

1. **先安全，后功能**：Secret、账号、权限、审计未闭环，不进入生产。
2. **先真值，后报表**：库存、财务、质量没有单一真值，不做经营分析。
3. **先闭环，后扩张**：先把采购到付款、销售到收款、计划到生产、订单到交付做通。
4. **先证据，后宣称**：没有证据的能力只能标记为“待验证”。
5. **先单租户稳定，再多租户规模化**：租户隔离和资源配额是规模化前提。

## 6. 结论

项目当前最大问题不是“功能不够多”，而是：

> **功能广度已经很大，但生产安全、跨域一致性、核心业务闭环和证据链没有同步达到企业级要求。**
